# Планер: продуктовый контракт и порядок реализации

02.11.2026. Требования владельца подтверждены в центральном чате. Статус: спецификация, не работающий сервис. Основной охват: все восемь направлений без Google Business; ограничения API см. SCHEDULER_CHANNEL_READINESS.md.

## Сценарий

Готовый проект → несколько каналов/подключённых назначений → проверка фото и текста каждого → «Сейчас» или общие дата/время → при необходимости время отдельно для назначения → окончательное подтверждение. Дальше сервер выполняет задания без открытого сайта.
Один проект может иметь несколько отдельных публикаций. Редактирование готового проекта не меняет уже утверждённые задания скрытно. Повторяющиеся правила и автоматический выбор «лучшего времени» не входят в первый этап: пользователь сам выбирает время.
WhatsApp: отдельные выбираемые назначения status/channel/client-message и их сочетания; пока официальный отправляющий API режима не подтверждён, режим недоступен для автоматической отправки с понятной причиной. E-Mail: выбранные клиенты, фото и текст, а не письмо владельцу по умолчанию.

## Пакет и задания

Предлагаемый новый контракт (не существующие API/таблицы):
- Пакет: владелец, projectId, версия, общая дата/время/Europe/Berlin, подтверждение, общий request key.
- Дочернее задание на каждое точное назначение: channel, connectionId и destination (Page/аккаунт/доска/CMS-блог/WhatsApp-режим/получатель email), собственная caption, materialSnapshotId, итоговый UTC instant + исходная зона/offset, собственные execution identity/revision/status/result.
- Несколько сайтов/блогов или адресатов не сводить к одному названию канала. Получатели E-Mail изолированы: не раскрывать другим клиентам список адресов.
- «Опубликовать сейчас» проходит тот же контроль доступа, подготовки и защиты от дублей; не обходить правила отдельным опасным shortcut.
- Создание пакета в БД атомарно; внешние публикации в разных сервисах НЕ атомарны. Отдельно показывать успех, отказ и неопределённый результат каждого назначения.

## Утверждение и время

Подтверждение фиксирует назначение, фото, точный текст и время. Изменение этих полей создаёт новую версию для подтверждения. При переносе/отмене проверять ожидаемую revision и факт начала отправки. Отмена не удаляет уже опубликованный внешний пост.
Хранить UTC и IANA zone; обрабатывать перевод часов Europe/Berlin: несуществующее время отклонять, повторяющееся время показывать с явным offset для выбора. Не использовать часовой пояс компьютера как скрытую настройку.
Для первого этапа предлагается точность выбора до минуты, без обещания публикации в точную секунду. Фактический момент зависит от выполнения задания и ответа провайдера; просроченные задания показывать отдельно. Политику просрочки определить до включения реальной отправки, не отправлять давние задания молча после простоя.

## Материалы и выполнение

До утверждения подготовить совместимую серверную версию фото и показать её. Сохранить неизменяемую ссылку на версию/контрольную сумму, не «последнее фото проекта». Установить правила удержания и удаления snapshot при удалении проекта/аккаунта.
Перед исполнением снова проверить владельца, действующее разрешение пользователя, доступ к назначению, тарифные права, отзыв подключения, срок токена, текущие лимиты и подготовленность файла. Уже отправленные назначения не повторять.
Периодический серверный запуск выбирает due задания, атомарно захватывает право исполнения и передаёт в очередь/исполнитель. Выбор Cron + очередь/Durable Object и account-wide сериализация — инженерное решение после проверки имеющегося прототипа, не активированная конфигурация. [Cloudflare scheduled](https://developers.cloudflare.com/workers/runtime-apis/handlers/scheduled/), [Cron UTC](https://developers.cloudflare.com/workers/configuration/cron-triggers/).
При неоднозначном сетевом результате не обещать exactly-once во внешних API: сохранять исходную identity, сверять результат при наличии официального способа, иначе требовать проверки. Повтор доставки очереди не должен автоматически повторять внешний POST. Безопасные повторные попытки и rate-limit backoff разрабатывать по отдельным провайдерам.

## Интерфейс

В проекте: галочки каналов/назначений, общий выбор времени и overrides, превью/редактор каждого текста, явное подтверждение списка отправок. У неподключённых/неподдерживаемых назначений — причина и путь подключения; ручное открытие не выдавать за scheduled publish.
В кабинете: пункт «Планер», общий календарь (месяц + список ближайших), фильтр проекта/канала, карточка задания, перенос/отмена до начала отправки, понятные статусы и время фактического результата. Клавиатура, немецкие подписи, мобильный список без широкой сетки. Стиль существующего приложения; не вводить новый шрифт.

## Последовательность работ

| Шаг | Ответственность | Проверяемый результат |
| --- | --- | --- |
| 1 | Backend + SQL, координация здесь | Проверить контракт пакета/отдельных назначений на существующем kernel/adapter; локальный D1 round-trip, owner isolation, immutable snapshot, revision и rollback. Без отправки |
| 2 | Backend + API | Локальные create/list/detail/reschedule/cancel, entitlements и разрешения; раздельные тексты/время. Недоступные коннекторы не дают создать утверждённое задание |
| 3 | Frontend | Галочки в проекте и единый планер на этих контрактах; mock-данные явно только в тестах, не production storage в localStorage |
| 4 | Backend + Testing | Фоновый исполнитель с fake-провайдерами: due/claim/повтор/потерянный ответ/частичный успех/отмена; подтверждение сохранности при закрытом браузере |
| 5 | API + Backend | Завершить диагностику Meta OAuth и подготовку JPEG; подключить реальное исполнение Instagram/Facebook после необходимых разрешений. Это очередность реализации, не исключение остальных каналов |
| 6 | API + Backend | Отдельные адаптеры Pinterest, X, LinkedIn, WordPress/Wix и далее Joomla/Drupal/Ghost/Webflow/Shopify/Blogger; порядок внутри этапа зависит от доступных контрольных аккаунтов |
| 7 | API + Backend | E-Mail по выбранным клиентам и официально подтверждённые режимы WhatsApp. Для остальных CMS/режимов — отдельная проверка write API, без неофициальной автоматизации браузера |
| 8 | Testing + контрольная точка | Доказательства E2E каждого включаемого назначения, ограниченный release и сверка production-версии; отдельное разрешение на deployment и включение отправки |

Названия направлений — распределение ответственности, а не утверждение, что задания уже отправлены в другие чаты. Все результаты и решения возвращаются в центральный чат.

## Обязательные проверки

- Десять проектов на разные дни/время; после закрытия браузера исполнитель не зависит от UI.
- Общая дата/время и индивидуальные overrides; Berlin DST, прошлое/некорректное время, задержка исполнения.
- Чужой проект/назначение, отозванный доступ, истёкший токен, изменение тарифа, удалённый snapshot; никаких чужих данных и неразрешённой отправки.
- Изменение текста/фото/времени требует новой версии подтверждения; stale update отклоняется.
- Дубликаты запросов/очереди, конкурирующие исполнители, rate limit, падение до/после внешней отправки; published не отправляется снова, unknown не превращается в автоматический retry.
- Разные подписи/совместимые фото, правильный получатель каждого задания, частичный успех без повторения успешных направлений.
- Списки E-Mail/телефоны/токены не попадают в GitHub, публичные URL и диагностические сообщения.
